# VidyaGanit AI tutor chat

The chat endpoint `POST /api/chat/message` (in `artifacts/api-server`) streams Server-Sent Events. It is NOT in the OpenAPI spec (raw SSE, hand-written fetch on the client) — so no Orval codegen applies to it.

## Models / integration
- Uses Replit AI Integrations (managed OpenAI/Anthropic/Gemini) via `@workspace/integrations-openai-ai-server`, `@workspace/integrations-anthropic-ai`, `@workspace/integrations-gemini-ai`. Requires the per-integration env vars (provisioned, not user-supplied).
- **Multi-model selector (all three portals):** the user picks a specific model in the chat header dropdown (`AiModelSelect.tsx`, grouped by provider via `<optgroup>`). The client sends a `chatModel` KEY (e.g. `gpt-5.4`, `claude-haiku-4-5`, `gemini-3-pro`) — NOT a provider. The server catalog `CHAT_MODELS` in `lib/aiChat.ts` resolves each key → `{provider, model}`; `normalizeChatModel(value)` defaults to `gpt-5-mini` for unknown/missing. `streamChat` branches on `provider` and uses the resolved `model` id. **Why a key not a raw model id:** keeps the OpenAPI enum, server catalog and UI labels in lockstep and prevents arbitrary/unsupported model ids from the client.
- The `chatModel` enum lives in the OpenAPI spec on BOTH `ChatMessageInput` and `ConsultantMessageInput` (contract-first → regenerate with `pnpm --filter @workspace/api-spec run codegen` after changing it). Adding/removing a model means editing FOUR places in lockstep: openapi enum (×2 schemas), `CHAT_MODELS` (server), `ChatModelKey`+groups (`AiModelSelect.tsx`). Only models listed in the ai-integrations-{openai,anthropic,gemini} skills are valid; never invent ids. This REPLACED the old `provider`-only field (`normalizeProvider`/`MODEL_BY_PROVIDER` are gone).
- Default stays `gpt-5-mini` (`chat.completions.create`, `stream:true`, `reasoning_effort:"low"`, `max_completion_tokens`, NO `temperature` — gpt-5 family rejects it) for low latency + credit conservation. Anthropic opus/sonnet/haiku all work with the existing `anthropic.messages.stream` call (do NOT set temperature/top_p/top_k or thinking budgets on opus-4-8 — it 400s). Image gen (`[[DRAW:]]`) is a SEPARATE selector (`imageModel`), unchanged.
- Images: `gpt-image-1` via `generateImageBuffer` (gpt-4o image gen is legacy per the ai-integrations-openai skill). For SPEED, `aiImage.generateImageDataUrl` calls it with `quality:"low"` — the tutor's inline diagrams are deliberately simple flat-vector with short labels, so the lowest gpt-image-1 quality tier renders acceptably while generating much faster/cheaper than the default high/auto. **Why:** image gen runs serially AFTER the text stream (the `[[DRAW]]` marker arrives at the very end, so it cannot start earlier); the quality tier is the only meaningful latency lever. The lib `generateImageBuffer(prompt,size,quality)` keeps `quality` default `"auto"` for backward compat; the app opts into `"low"` at the call site. This one change covers all three portals (student/tutor `chat.ts`, parent `parent.ts`) since both route through `generateImageDataUrl`.

## SSE contract (keep backward compatible)
Events: `{chunk}` (text), `{drawing:true}`, `{image:"data:image/png;base64,..."}` + `{imageAlt}`, `{imageError:true}`, and terminal `{done,xpAwarded,newBadges}`. The frontend splits the stream buffer on `\n\n`; `JSON.stringify` escapes newlines so a big base64 image stays a single SSE line.

## `[[DRAW: ...]]` marker
The model appends `[[DRAW: <prompt>]]` at the END of a reply when a picture would help. The server must strip it from the streamed text before the client sees it. Streaming stripper withholds only the longest trailing suffix of accumulated text that is a prefix of the literal `"[[DRAW:"` (and everything from a full marker-start onward). This avoids leaking a partial `[[` and avoids permanently stalling on unrelated `[[` (e.g. matrix notation) — unrelated text is released on the next chunk.

## Auth / abuse hardening (chat only)
The chat endpoint is gated by `requireAuth` (see `middlewares/auth.ts`): identity comes from a stateless HMAC-signed `vg_session` httpOnly cookie (`lib/session.ts`, signed with `SESSION_SECRET`), set on `/auth/login` + `/auth/register`. The route derives `vidyaId` from the cookie and IGNORES the body `vidyaId` (fixes IDOR/XP-spoofing). Also: in-memory fixed-window rate limits (20/min + 200/hour per identity) and input caps (message ≤1500 chars, history `MAX_HISTORY_ENTRIES`×`MAX_HISTORY_ENTRY_LEN`). **`MAX_HISTORY_ENTRIES` is 200 (NOT 20) on purpose** — the AI must remember the FULL conversation a student/parent/tutor has worked through, not just recent turns; the same constant exists identically in `chat.ts` (student) AND `parent.ts` (parent + tutor consultant), so change BOTH together. It is a generous abuse/context-window ceiling, not a "recent window"; do not lower it back to ~20 (that silently makes the AI forget earlier parts of long chats). Both routes use the 12mb `largeJson` body parser so a full history fits; there is no `maxItems` on the OpenAPI `history` array. Frontend sends `credentials:"include"` and shows friendly 401/429 messages.

**Why same-origin cookies work:** frontend (`/`) and API (`/api`) are one origin via path-based proxy routing, so the cookie auto-flows; no CORS-credentials dance needed.

Profile routes (`/profile/:vidyaId*`) are now also gated by `requireAuth` + `requireSelf` (ownership: `req.vidyaId === req.params.vidyaId`, else 403) — same IDOR class fixed there. Safe because both dashboards only fetch their own `vidyaId`.

Rate limiting is backed by a shared Postgres table `rate_limit_buckets` (fixed-window, key=`prefix:identity:windowStart`, atomic `INSERT ... ON CONFLICT DO UPDATE count = count + 1`), so limits hold across instances/restarts. **Does NOT fail open:** on DB error it falls back to a bounded per-instance in-memory limiter (cost protection must survive DB outages — flagged in review). 

**Note:** the chat body Zod schema still *requires* `vidyaId`, but the value is IGNORED for identity (cookie wins). The frontend still sends it; don't rely on it server-side.

**Caveat:** users logged in BEFORE cookies existed (localStorage-only) get 401 on chat until they log in once more.

## Compliance logging (Parent Dashboard groundwork)
Every tutor turn is persisted append-only to `chat_messages` (sessionId, studentVidyaId→users.vidyaId, role, content, createdAt). Keyed by the cookie-derived `vidyaId`, never the body. The client sends a `sessionId` (added as optional to OpenAPI `ChatMessageInput`) generated per conversation and regenerated on "clear chat". Inserts are best-effort (wrapped in try/catch + `req.log.error`) so a logging failure never breaks the live chat. The AI-failure fallback message shown to the child is also persisted (so the audit log matches what was displayed). NOT persisted: client-only input-sanitizer nudges (they never reach the server — deliberate scope choice).

## Syllabus knowledge (all three AI surfaces)
`buildSyllabusKnowledge(studentClass, board)` in `lib/curriculum.ts` renders the `CURRICULUM` data (Classes 4–7) as a board-aware text block and is injected into ALL THREE prompts: the student Socratic tutor (`buildTutorSystemPrompt`, `lib/tutor.ts`) and BOTH counselor personas (`buildCounselorSystemPrompt`, `lib/counselor.ts` — parent Strategy AI + tutor AI Coach). It names CBSE/NCERT, ICSE/CISCE, State Boards, tells the AI to align to the learner's own `board` (defaults to CBSE when null), details the learner's class in full + summarises the other classes, and instructs staying within class level. When no class is known (e.g. tutor with no student picked) it details all four classes. **Rule:** if you add a new AI surface, feed it `buildSyllabusKnowledge` too. **Import safety:** `curriculum.ts` has only a type-only import of `Topic` from `tutor.ts` (erased at runtime), so `counselor.ts`/`tutor.ts` can both value-import `curriculum.ts` with no runtime cycle.

## Topical guardrail
`buildTutorSystemPrompt` (`lib/tutor.ts`) has a strict "TOPIC GUARDRAIL" block: refuse all non-maths queries (movies, games, stories, code, etc.) and playfully redirect to maths. This is prompt-only; there is no server-side topic classifier.

## No-spoon-feeding rule
`buildTutorSystemPrompt` also has a "NO SPOON-FEEDING" block as strict as the Golden Rule: when working the student's OWN problem the coach must never write the fraction for them, never state the numerator/denominator value, and never give the exact divisor/HCF — it must ask open questions so the student produces each number. It MAY still teach with a different illustrative example using other numbers. (Added after live testing showed the AI handing over "4/8" and "divide by 4".)

## File attachments (paperclip + camera)
Students can attach ANY file type to a chat message (paperclip = `accept="*/*"`, camera = `accept="image/*" capture="environment"`). Client reads the file via `FileReader` → base64 data URL and sends it as an optional `attachment {name, mimeType, dataUrl}` in the JSON body (added to OpenAPI `ChatMessageInput` → regenerated `SendChatMessageBody`). Server (`routes/chat.ts`): images → multimodal `image_url` content for vision; readable text (text/csv/json/xml/yaml) → decoded + inlined; other binary (pdf/docx) → coach describes the file and asks the student to photograph/retype. A message may be sent with an attachment and EMPTY text; gibberish `validateStudentInput` is skipped when an attachment is present.

**GOTCHA — body size limit:** attachments are big base64 data URLs (cap ~8MB → ~11.5MB encoded, `MAX_ATTACHMENT_DATAURL_LEN`). Express's default `express.json()` limit is ~100kb, which silently rejects real attachments with 413 before the route runs. `app.ts` therefore applies a route-scoped `express.json({ limit: "12mb" })` ONLY for `/api/chat/message`; every other route keeps the small default to limit abuse. The route handler also enforces its own size cap as second-line defense. **Why:** if you ever add another upload endpoint, give it its own large-limit parser — do NOT raise the global limit.

## Voice input (mic button)
ALL THREE AI portals (student `SocraticChat`, parent Strategy + tutor Coach `ParentConsultantChat`) now share ONE hook `src/hooks/useLiveSpeech.ts` — browser **Web Speech API** (`window.SpeechRecognition ?? window.webkitSpeechRecognition`), `interimResults=true` + `continuous=true` so partial text streams into the input box AS the user speaks. The parent/tutor side previously used MediaRecorder + the server `/consultant/transcribe` route (only transcribed AFTER stop — the "doesn't transcribe live" complaint); that client path is gone (server route left in place, now unused). `speechLocale(lang)` maps the app's 23 language codes → BCP-47.

**Liveness/flakiness rule (the "sometimes not working" fix):** Chrome's recognizer auto-ends after a silence pause. To stay live we restart on `onend` while `wantListeningRef` is true. The trap: handlers must be guarded by an **instance-identity check** (`if (recognitionRef.current !== recognition) return;`) in `onresult`/`onerror`/`onend`, and `stop()` must null the ref BEFORE calling `abort()`. Without this, a stop→quick-restart lets a stale instance's `onend` call `start()` on the new (already-running) recognizer → throws → silently disables dictation. Accumulate finals across restarts in `finalTranscriptRef` so nothing is lost.

TS DOM lib lacks these types — ambient declarations in `src/types/speech.d.ts`. Voice goes through the SAME message path as typed text, so the math-only TOPIC GUARDRAIL + `validateStudentInput` apply automatically. **Env caveat:** mic needs iframe permission policy (`allow="microphone; camera"`) — fails in restrictive embeds (e.g. canvas iframe); test in the real preview/published tab. Web Speech API is Chromium/Safari only (Firefox unsupported) — `supported` flag drives the unsupported-browser message.

## GOTCHA — Fast Refresh & mixed exports (caused "buttons not working")
`SocraticChat.tsx` previously exported BOTH a constant (`BADGE_CATALOG`) and the default component. react-refresh requires a file to export ONLY components to hot-patch it; the mixed export made every edit fail Fast Refresh ("export is incompatible") and fall back to a full reload that sometimes left STALE code in the browser — so newly-wired buttons appeared "not working" until a hard refresh. **Fix/rule:** keep non-component exports (constants, types, helpers) OUT of component files — `BADGE_CATALOG` now lives in `src/lib/badges.ts`. **Why it matters:** symptom looks like a broken feature but is really stale HMR; check the vite HMR logs for `invalidate ... Could not Fast Refresh` before debugging the feature code.

## Parent Dashboard (analytics + history + Strategy AI counselor)
The Parent Dashboard (`pages/ParentDashboard.tsx`) has its profile/linked-students flow PLUS three student-aware tabs backed by parent routes in `routes/parent.ts` (all `requireAuth + requireSelf`, parent identity from cookie). Per-student access is gated by `getLinkedStudent(parentVidyaId, studentVidyaId)` — if a `studentVidyaId` is supplied but NOT linked, the route MUST return 403, never silently fall back to general advice (this exact soft-fail was flagged in review on the consultant/message route). The student picker only ever passes linked children, so 403 is an edge case but enforced server-side regardless.

- **Analytics** GET `/parent/:id/consultant`-adjacent: mastery is an honest activity-estimate `min(100, round(questionsPracticed*12.5))`, topics via `detectTopic` (fraction/decimal/divide). NOT a test score — labelled as such in UI; don't present it as real assessment.
  - **Single source of truth:** the mastery/topics computation lives in ONE helper `computeStudentAnalytics(studentVidyaId)` in `lib/analytics.ts` (with `ANALYTICS_TOPICS`). BOTH the parent route (`/parent/:id/students/:sid/analytics`) and the student self route (`/profile/:vidyaId/analytics`, gated `requireAuth + requireSelf`) call it and spread its result into their respective `*AnalyticsResponse`. **Why:** student & parent views must never drift — change the formula/topics in one place. The student self-view (`StudentProgress.tsx`, "My Progress" tab) reuses the same `exportReport` PDF/CSV util as the parent's `ProgressAnalytics`.
- **Strategy AI** POST `/parent/:id/consultant/message` is its OWN hand-written SSE endpoint (mirrors the tutor chat pattern, NOT in OpenAPI): events `{chunk}`, `{drawing:true}`, `{image,imageAlt}`, `{imageError:true}`, terminal `{done,sessionId}`. Counselor persona/prompt in `lib/counselor.ts` (`buildCounselorSystemPrompt`), model `gpt-5-mini`. Parent turns persisted append-only to `parent_chat_messages`. This same route + the shared `ParentConsultantChat.tsx` component (variant `parent` = Strategy AI, variant `coach` = tutor AI Coach) BOTH support inline image generation with a user-selectable model (`ImageModelSelect`: gpt-image-1 / Nano Banana / Nano Banana Pro) sent as `imageModel` in the body, just like the student chat. Both counselor personas may emit `[[DRAW: ...]]`; the route withholds/strips it exactly like `chat.ts`.
  - **GOTCHA (marker leak on error path):** persist the assistant reply from `full.slice(0, sent)` (what was actually streamed, marker already withheld), NOT `full.replace(DRAW_MARKER_RE,"")`. The regex only strips a *complete* `[[DRAW:...]]`; a stream that errors mid-marker leaves a partial `[[DRAW: foo` that the regex misses and would persist into saved history. `sent` is always marker-safe. Same principle applies if you ever add markers to other SSE routes.
- **Transcribe** POST `/parent/:id/consultant/transcribe` takes `{audio:dataUrl, mimeType, language}` → `{text}`, uses `speechToText` + `ensureCompatibleFormat` from `@workspace/integrations-openai-ai-server/audio` (`gpt-4o-mini-transcribe`). **NO LONGER CALLED by the client** — the parent/tutor mic switched to the shared live `useLiveSpeech` Web Speech hook (see Voice input section). Route left in place but unused; safe to delete if you also drop its body-parser entry.

**GOTCHA — body limit:** the message + transcribe routes need the large JSON body parser too. `app.ts` matches them with `PARENT_LARGE_BODY_RE = /^\/api\/parent\/[^/]+\/consultant\/(message|transcribe)$/` alongside `/api/chat/message`. Any new upload route needs its own large-limit entry.

## i18n (parent-side native language selector)
`src/lib/i18n.tsx` provides `LanguageProvider`/`useLanguage`/`LANGUAGES` with full en/ta/hi/te dicts, persisted to localStorage key `vidyaganit_lang`. Currently wraps ONLY the Parent Dashboard (the chosen `language` is also forwarded to the counselor + transcribe endpoints so AI replies/transcripts come back in that language). The student-facing app is NOT yet wrapped — extending i18n app-wide is a known follow-up. Keep the provider/hook/consts in this lib file (non-component exports) separate from components for Fast Refresh.

## Automated API tests (Vitest)
`artifacts/api-server` now has Vitest tests (`pnpm --filter @workspace/api-server run test`; registered as the `test` validation). Non-obvious setup needed to make them run: workspace pkgs export raw `.ts`, so `vitest.config.ts` must inline `[/@workspace\//]` (`server.deps.inline`) and set `resolve.conditions: ["workspace","import","node"]` — otherwise the `@workspace/*` `.ts` imports are externalized and fail. Tests hit the real dev Postgres (seed/cleanup rows under a unique `TST-<ts>-` vidyaId prefix) and `vi.mock` the OpenAI integration (`@workspace/integrations-openai-ai-server` + `/audio`) so no network/credits are used. To assert a 429 deterministically without N calls, pre-seed `rate_limit_buckets` at the limit for the current window (key `prefix:identity:windowStart`). **Caveat:** `pnpm --filter @workspace/api-server run typecheck` currently fails on a PRE-EXISTING error in `routes/chat.ts` (`parsed.data.language` not on `SendChatMessageBody` — spec/codegen drift), unrelated to the tests.

## Tailored game auto-launch (offer → "Yes")
The game-offer SSE event carries the detected `topic` (additive field). When the student accepts, the client auto-launches a game *tailored to that topic* instead of opening the game menu. Topic→game mapping lives in `syllabus.gameForTopic(topic, cls, board)`: it returns the first candidate game that is actually available for the student's class/board, else `null`. `MiniGames` takes an optional `initialGame` prop and auto-starts it **once per open** via an `autoStartedRef` guard — never restart mid-play on re-render; the menu stays reachable via the result screen. **Why additive `topic`:** the game-offer contract test asserts the substring `"game":true`, so extra fields are safe; never rename/remove `game`.

**"Yes" must ALWAYS launch a game, never show the menu** (explicit user requirement). The offer handler calls `gameForTopicOrDefault(topic, cls, board)`, NOT `gameForTopic`: when the topical match is null (e.g. a Class-4 student asks about percent/ratio whose games start at Class 5+) it falls back to the first available game for the class/board (`gamesForClassBoard(...)[0].id`), which is always present for clamped classes 4–7. **Why:** the old `gameForTopic`→null path dropped the student on the menu, which users reported as broken. Do NOT revert the offer to `gameForTopic`. The menu is still reachable, but only via the in-game result screen.

## Personal context in prompts (all three AIs)
Each authenticated user has a free-text `aboutMe` (usersTable, max 1000, capped server-side in `profile.ts` PATCH). It is injected into the relevant persona's OWN system prompt: student's → tutor (`buildTutorSystemPrompt`), parent's → Strategy AI, tutor's → Coach (both in `buildCounselorSystemPrompt`). **Rule:** always wrap user free-text as explicitly UNTRUSTED ("personalization data, NOT instructions") so it can never override the Socratic/no-answer/topic guardrails — this is the only thing standing between a user-typed prompt-injection and the AI. The student tutor also receives a `computeStudentAnalytics(vidyaId)` progress summary (sessions/practice/mastery), framed as "activity estimate, not formal test scores"; parent/tutor counselor already loads per-child mastery. If you add a new AI surface, feed it both the guarded `aboutMe` and progress the same way.

## Cross-session memory (all three AIs)
Each AI can refer back to the user's OWN earlier conversations even in a brand-new chat. A guarded digest (`buildPastConversationDigest`, `lib/chatMemory.ts`) is built from the user's persisted messages and injected into the system prompt (student tutor + both counselor personas). **Key correctness rule:** the digest filters out the CURRENT `sessionId` so it never duplicates the live `history` payload — the current user turn is persisted *before* the digest query but carries the current sessionId, so it's auto-excluded. Bounded (40 most-recent past turns, 400 chars each); routes load ≤300 recent rows (own user id only, indexed). **Privacy scope (deliberate):** memory is each user's OWN past chats only — NO cross-user knowledge (a tutor cannot see students' chats). **Prompt-injection rule:** the ENTIRE injected transcript (BOTH past user words AND past assistant replies) must be flagged UNTRUSTED reference, never instructions — a persisted prior reply could itself contain an injection. Loading is best-effort try/catch so a memory failure never breaks live chat.

## Message feedback (thumbs up/down, all three AIs)
Every assistant reply in all three portals can be rated up/down, persisted per message and restored on reload. Stored as a nullable `feedback` text column (`up|down|null`) on BOTH `chat_messages` and `parent_chat_messages`. **Contract gotcha:** the feedback feature added `id`+`feedback` as REQUIRED to `ChatSessionMessage` and `ConsultantMessage` in the OpenAPI spec — so EVERY server handler returning one of those shapes must map `id` and a normalized `feedback`, or the response Zod `.parse` throws 500. There are MULTIPLE such handlers per message type (e.g. the consultant *session* GET and the consultant *history* GET both build `ConsultantMessage`); miss one and only that endpoint 500s. The session-list endpoints use their OWN message shape (no `id`), so they're unaffected. Assistant inserts use `.returning({ id })` and emit `messageId` in the terminal SSE `done` event so the client can attach feedback immediately. Feedback write routes are gated `requireAuth + requireSelf` with a SQL predicate on `(messageId AND owner vidyaId AND role='assistant')`, returning 404 on mismatch (no IDOR). Frontend does optimistic toggle with rollback on error; buttons render only when `!isStreaming && !isDrawing && dbId != null`.

## Frontend input sanitizer
`validateStudentInput` in `SocraticChat.tsx` intercepts gibberish/emoji-spam BEFORE calling the API and shows a friendly nudge. **Must stay Unicode-aware:** the "has meaning" check uses `/[\p{L}\p{N}]/u` (+ maths operators), NOT `[a-zA-Z0-9]` — an ASCII-only check wrongly blocks Hindi/Tamil/Devanagari input, a real break for this Indian-student app. Repeated-char/keyboard-mash heuristics are intentionally ASCII-only so they don't false-positive on Indic scripts.
